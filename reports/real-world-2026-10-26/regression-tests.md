# Top 10 recommended regression tests

Items 1 and 2 are implemented by the six frozen SNAPSHOT regressions in this PR. The other items remain recommended expansions; external coverage is recorded separately. Retain native resolver evidence and assert selected versions, exact findings, classifications, checked counts, and warning/strict exits. Existing fixtures already cover several basic cases; extend them with these real-world conditions.

| Priority | Test | Required oracle and assertions |
| --- | --- | --- |
| 1 | Timestamped SNAPSHOT alias, aligned consumer | Freeze a local Maven repository containing a Boot 4 BOM and timestamped SNAPSHOT JAR metadata. Run artifact resolution, not only collection. A versionless dependency resolved from that BOM must yield zero drift and strict exit 0. This reproduces BBG-001 without a mutable public repository. |
| 2 | Explicit older timestamp under the same base SNAPSHOT | Native metadata selects a newer timestamp, but a consumer explicitly pins an older available timestamp. Preserve this genuine drift after fixing alias equivalence; a blanket `getBaseVersion()` conversion must not hide it. |
| 3 | Mixed real drift and SNAPSHOT aliases | Replay the Gateway pattern: aligned timestamped Boot artifacts plus real gRPC version differences. Only the genuine selected differences appear; the guard must not emit dozens of Boot false positives or label them overrides. |
| 4 | Reactor with BOM-less aggregators and supported leaf | Replay Spring Boot Admin structure with `-pl/-am/-T2`. Assert the documented UNKNOWN at BOM-less projects and strict failure there, while an explicitly scoped Boot leaf passes. Verify module-specific execution/log attribution and document correct consumer-only wiring. |
| 5 | Metadata tree succeeds while sibling JAR is absent | Use a reactor/local sibling POM with an unavailable binary. Native `dependency:tree` can return 0 while `dependency:resolve` fails. The guard must report UNKNOWN, warning 0, strict nonzero; never count a metadata-only graph as fully analyzed. |
| 6 | Native Gradle platform combined with Spring DSL rules | Keep the DSL plugin, add the same Boot platform, then vary explicit versions, constraints, force and DSL properties independently. Compare to a clean native-platform project. A declaration the DSL overrides is not selected drift; actual changed selections must use a pristine BOM baseline and honest origin. |
| 7 | Gradle child-project origin matrix | Apply the guard to a child only. Independently select an explicit version, a root constraint, a transitive bridge request, and a force. Assert DIRECT_OVERRIDE, MANAGED_OVERRIDE, TRANSITIVE_DRIFT and UNKNOWN_ORIGIN respectively when native reasons support them. Confirm the parent and sibling graphs do not contaminate that child. |
| 8 | Configuration and platform boundaries | Runtime aligned, test runtime drifted; compare four default classpaths. Repeat with `platform` and `enforcedPlatform`; verify native selected versions and proper configuration labels. Add a custom resolvable configuration and a deliberately unresolvable one, asserting incomplete analysis instead of silent exclusion. |
| 9 | Broad, duplicated graph with repeatable resource measurements | Use a frozen native graph with thousands of components and repeated paths, including typed/classified artifacts. Assert deduplicated identities, deterministic reports and identical graph hashes. Measure three warmed native/guard pairs, peak JVM RSS and explicit time/memory budgets. Whole default reactors are now measured, but no single resolved module exceeds 1,500 components. |
| 10 | Offline/error diagnostics with synthetic credentials | Replay warmed resolution and a missing artifact using a local test repository/proxy that fails with URL userinfo and token-like strings. Assert UNKNOWN and strict failure, no secret in guard reports, and deterministic offline behavior. Keep native build-tool logs separate from guard-owned diagnostics. |

Remaining gaps: a single graph above 1,500 components, comprehensive custom configurations/rules/substitutions, production resource budgets and mirror/proxy error sanitization. See coverage-matrix.md for the exact external cases exercised.
